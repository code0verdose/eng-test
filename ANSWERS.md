# Ответы

Примеры из двух моих рабочих проектов: CRM для юридических фирм и B2B-маркетплейс. Оба на Node.js, PostgreSQL и React.

## Аутентификация

**Проект с другой техникой: серверные сессии.**

В маркетплейсе вход без пароля, по коду на почту или через OAuth. После входа сервер создаёт сессию в базе, а в httpOnly cookie уходит только её случайный id. На каждый запрос сессия достаётся из базы по первичному ключу.

JWT я бы там не выбрал:

- **Нужен мгновенный отзыв.** Когда пользователя банят или сбрасывают ему второй фактор, все его сессии удаляются сразу, в той же транзакции. С JWT пришлось бы ждать истечения токена или вести чёрный список, то есть всё равно ходить в хранилище.
- **Второй фактор привязан к сессии.** Отдельные действия, например подпись договора, требуют недавно пройденного второго фактора. С сессией это одно поле на сервере, с JWT пришлось бы выпускать новый токен.
- **Запрос в базу почти бесплатный.** Одна база, поиск по первичному ключу. Главный плюс JWT, проверка без обращения к хранилищу, здесь ничего не даёт.

Для внешних партнёров там API-ключи: в базе хранится только хеш ключа, у ключа есть права на конкретные операции, отзыв одной кнопкой. Для машинного доступа это удобнее токенов с коротким сроком.

**Проект, где вместо JWT я бы выбрал другое.**

В CRM сделан JWT: access-токен на 15 минут в памяти клиента и refresh в httpOnly cookie с ротацией. Схема рабочая, но выигрыша от JWT там нет:

- сервер один;
- для refresh-токенов всё равно используется Redis;
- access-токен нельзя отозвать до истечения: уволенный сотрудник ещё 15 минут видит данные клиентов.

Сессия в Redis закрыла бы то же самое проще, с мгновенным отзывом и коротким id в cookie вместо токена на несколько сотен байт в каждом запросе.

JWT я бы взял, когда токен проверяют несколько независимых сервисов или внешние стороны, у которых нет доступа к нашему хранилищу сессий. Для обычного веб-приложения с одной базой по умолчанию беру сессии.

## Идентификация

Uuid у меня стандартный первичный ключ, но несколько раз его одного не хватило.

- **Uuid не задаёт порядок.** В истории изменений у нескольких записей одной правки оказалось одинаковое время создания. Сортировка по времени давала случайный порядок, а сортировать по uuid v4 бессмысленно. Пришлось добавить отдельный порядковый номер.
- **Людям нужны короткие номера.** Номер документа или ссылку на платёж диктуют по телефону и вписывают в назначение банковского перевода. Uuid для этого не годится, поэтому рядом с ним хранится отдельный человекочитаемый номер с уникальным индексом.
- **Пагинация.** По uuid нельзя листать «следующую страницу» по порядку, поэтому курсор строится по паре (время создания, id). Без составного индекса под эту пару список в админке делал полный проход по таблице.
- **Где мог бы стать проблемой.** Случайный uuid v4 вставляется в произвольное место индекса. На больших таблицах с частой вставкой (логи, события) это раздувает индекс и ухудшает работу кеша. Там я бы взял uuid v7, где в начале время, или обычный автоинкремент.

## Организация кода

Последние проекты я делаю на Express с разделением на слои: бизнес-логика, интерфейсы того, что ей нужно снаружи (база, платежи, почта), и их реализации. Зависимости собираются вручную в одном месте. До этого работал с NestJS.

**Что реально помогло.**

- **Замена внешнего сервиса.** В маркетплейсе оплату комиссии через Stripe заменили банковским переводом по счёту. Удалили реализацию для Stripe и обработчик вебхуков, а бизнес-логику комиссии почти не тронули, потому что она работала с интерфейсом, а не со Stripe.
- **Тесты без базы.** Бизнес-логика тестируется с подменёнными реализациями в памяти. Такие тесты быстрые, их можно писать тысячами, а тесты на настоящей базе остаются только для слоя работы с данными.
- **Проверка прав прямо в объявлении маршрута.** Функция проверки ролей заодно помечает маршрут разрешёнными ролями. Из этих меток автоматически собирается таблица «роль × маршрут», и любое расширение прав видно на ревью.
- **Модули в NestJS.** По модулю сразу видно, что он отдаёт наружу и от чего зависит. Guards и pipes позволяют один раз написать проверку ролей и валидацию и не дублировать их по контроллерам.

**Что создавало сложности.**

- **Циклические зависимости в NestJS.** Двум сервисам из разных модулей становятся нужны друг друга, появляется `forwardRef`, и граница между модулями размывается. Фреймворк позволяет так сделать быстро, и это остаётся в коде.
- **Неявная цепочка декораторов.** Что произойдёт с запросом, определяется guards и interceptors на нескольких уровнях сразу, и при отладке эту цепочку приходится восстанавливать в голове.
- **Ручная сборка растёт.** Без DI-контейнера файл, где собираются все зависимости, в большом проекте разрастается до тысяч строк. Ошибку ловит компилятор, но читать его тяжело. Это честный минус моего подхода.

## Реактивность

**Где реактивность мешала.**

Когда у тебя есть объект со своим долгоживущим состоянием, а React хочет его пересоздать.

- **WebGL-анимация.** Если передать параметры анимации в зависимости `useEffect`, при каждом изменении пропса React сносит эффект, и графический контекст создаётся заново: фон мигает. Пришлось создавать контекст один раз, а меняющиеся параметры читать из ref.
- **Текстовый редактор со своим состоянием документа.** Двусторонняя синхронизация с React давала цикл: редактор отдаёт текст, React кладёт его обратно, редактор снова сообщает об изменении. Пришлось запоминать последнее отданное значение и не возвращать его обратно.

**Рендер на другом принципе.**

- **Canvas.** Анимированный радар я рисовал на canvas циклом `requestAnimationFrame`, а React только монтировал элемент. Цикл останавливается, когда радар уходит за экран. Для анимации на 60 кадров в секунду это проще и дешевле, чем гонять её через состояние.
- **SolidJS.** На сайте юридической коллегии (Astro и SolidJS) картинка плавно масштабируется при скролле. В Solid функция компонента выполняется один раз, а при изменении сигнала обновляется только стиль одной картинки. В React тот же код на `useState` перерисовывал бы компонент на каждом кадре. Минусы Solid: props нельзя деструктурировать, иначе пропадает реактивность, и экосистема заметно меньше.

**Что неудобно в React.**

- **Мемоизация руками.** Чтобы длинный список не перерисовывался целиком при изменении одного элемента, нужны `memo`, стабильные колбэки и стабильные ссылки в селекторах. Если селектор возвращает `items ?? []`, на каждый вызов создаётся новый пустой массив, и компонент перерисовывается без причины.
- **`useEffect` для синхронизации состояния.** Это почти всегда лишний рендер и источник гонок. Я стараюсь обходиться без него: производное значение считаю при рендере, реакцию на действие пишу в обработчике, сброс формы делаю через `key`.
- **Внешние источники.** Тема оформления, медиазапросы, общий таймер: если в каждом компоненте свой `useState` с подпиской, значения расходятся между компонентами. Правильное решение, `useSyncExternalStore`, есть, но о нём нужно знать заранее.

Если она крупная и плохо декомпозирована, например полноценный сервис с CRUD, контрактами и бизнес-логикой на бэке и на фронте, на неё может уйти пара дней.
