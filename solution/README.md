# The Last of Guss: моё решение

Реализация задания из [TASK.md](../TASK.md). Исходное решение в `server/` и `client/` в корне репозитория не тронуто. Здесь своё решение с нуля.

- **Сервер:** Node.js 22, TypeScript (strict), Fastify, Drizzle, PostgreSQL.
- **Клиент:** React 19, TypeScript, react-router, Vite, TanStack Query, Mantine.

## Запуск

Нужны Node.js 22 и PostgreSQL. Базу можно поднять в Docker:

```bash
docker run -d --name guss-pg -e POSTGRES_PASSWORD=postgres -e POSTGRES_DB=guss -p 5432:5432 postgres:16-alpine
```

Сервер:

```bash
cd server
cp .env.example .env
npm install
npm run build
node dist/index.js
```

При старте сервер сам применяет миграции из `migrations/`. Их можно запускать одновременно с нескольких инстансов, потому что применение защищено advisory lock.

Клиент:

```bash
cd client
npm install
npm run dev
```

Откройте http://localhost:5173. Dev-сервер Vite проксирует `/api` на `http://localhost:3000`.

**Пользователи.**

- Входите под любым именем: при первом входе пользователь создаётся.
- Имя `admin` даёт роль администратора, имя `Никита` даёт роль nikita, остальные становятся выжившими.

**Тесты.** Серверу нужен Docker, тесты сами поднимают Postgres. Вместо этого можно задать `TEST_DATABASE_URL`.

```bash
cd server && npm test
cd client && npm test
```

## Как устроено

### Тап и гонки

Тап выполняется одним SQL-запросом (`src/infrastructure/repositories.ts`, метод `tap`):

- **Проверка раунда.** Раунд должен быть активен по часам базы в момент запроса: `now() >= start_at AND now() < end_at`.
- **Очки игрока.** Строка игрока в раунде создаётся или обновляется через `INSERT ... ON CONFLICT DO UPDATE`. Эта команда блокирует строку, поэтому параллельные тапы одного игрока применяются по очереди, и ни один не теряется. Каждый одиннадцатый тап считается за 10 очков.
- **Общий счёт раунда** увеличивается на очки этого тапа в том же запросе.

Отдельной транзакции не нужно: один запрос атомарен. Тест `test/tap.integration.test.ts` проверяет это на настоящем Postgres. Три пула соединений, то есть три инстанса бэкенда, одновременно отправляют по 100 тапов от трёх игроков. Ни один тап не потерян, а общий счёт раунда равен сумме очков игроков.

### Несколько инстансов

- **Состояния в памяти процесса нет.** Сессии хранятся в базе, поэтому запрос можно обслужить любым инстансом.
- **Одни часы для всех.** Время старта и конца раунда и проверка активности считаются по часам базы, а не по часам Node-процесса. Часы трёх контейнеров могут расходиться, а часы базы у всех одни.
- **Часы клиента.** Сервер отдаёт `serverTime`, и клиент ведёт обратный отсчёт по часам сервера. Неверные часы на устройстве игрока игру не ломают.

### Аутентификация

Вход по имени и паролю создаёт сессию в базе. Токен уходит в httpOnly cookie с SameSite=Lax, а в базе хранится только его SHA-256 хеш. Выход удаляет сессию на сервере сразу. Пароли хешируются scrypt из `node:crypto`, без нативных зависимостей.

### Структура сервера

- `src/domain/`: правила игры без зависимостей (очки, роль по имени, статус раунда).
- `src/application/`: сценарии (вход, раунды, тап) и интерфейсы того, что им нужно снаружи.
- `src/infrastructure/`: реализации этих интерфейсов на Drizzle и PostgreSQL, хеширование паролей, миграции.
- `src/http/`: маршруты Fastify, сессия из cookie, единый формат ошибок `{ error: { code, message } }`.
- `src/index.ts`: единственное место, где интерфейсы связываются с реализациями.

### API

| Метод | Путь | Что делает |
| --- | --- | --- |
| POST | `/api/auth/login` | вход или регистрация, ставит cookie сессии |
| POST | `/api/auth/logout` | выход, удаляет сессию |
| GET | `/api/auth/me` | текущий пользователь |
| GET | `/api/rounds` | активные и запланированные раунды |
| POST | `/api/rounds` | создать раунд (только admin) |
| GET | `/api/rounds/:id` | раунд, мои очки, итоги после завершения |
| POST | `/api/rounds/:id/taps` | тап, возвращает мои очки |
| GET | `/api/health` | проверка живости процесса, без обращения к базе |

Все ошибки приходят в одном формате `{ error: { code, message } }`:

- **400** неверные данные или битый JSON;
- **401** нет сессии или неверный пароль;
- **403** не админ;
- **404** раунд или адрес не найден;
- **409** раунд не активен;
- **413** слишком большое тело запроса;
- **415** неподдерживаемый Content-Type.
- **500** внутренняя ошибка, без подробностей в ответе; подробности уходят в лог.

## Переменные окружения

| Переменная | По умолчанию | Что задаёт |
| --- | --- | --- |
| `DATABASE_URL` | обязательна | строка подключения к PostgreSQL |
| `ROUND_DURATION` | обязательна | длительность раунда, секунды |
| `COOLDOWN_DURATION` | обязательна | обратный отсчёт до старта, секунды |
| `PORT` | 3000 | порт HTTP |
| `CORS_ORIGIN` | `http://localhost:5173` | адрес фронтенда, если он на другом домене |
| `COOKIE_SECURE` | false | `true` за HTTPS: cookie сессии уходит только по HTTPS |
| `SESSION_TTL_HOURS` | 24 | время жизни сессии |
| `TRUST_PROXY_HOPS` | 0 | сколько reverse proxy стоит перед приложением; от остальных `X-Forwarded-For` не принимается |

## Развёртывание: 1 база, прокси, 3 бэкенда

- В образ кладутся `dist/` и `migrations/`, процесс запускается из папки `server/`.
- Бэкенды стартуют после того, как база стала healthy (`depends_on: condition: service_healthy`). Если базы нет, процесс сразу завершается с кодом 1 и не висит.
- Миграции можно применять при старте всех трёх инстансов: их сериализует advisory lock. Таймаут запросов к базе на миграции не действует, поэтому долгая миграция или ожидание чужой не прервутся.
- Если база перезапустилась или разорвала соединения, инстансы не падают: пул заменяет сломанные соединения. На запросы к базе стоят таймауты.
- По SIGTERM сервер перестаёт принимать новые запросы, дожидается текущих и выходит. Если запрос завис, процесс завершается принудительно через 10 секунд.
- `/api/health` отвечает без обращения к базе, это проверка живости процесса.

## Осознанные упрощения

Для тестового задания я оставил несколько вещей, которые в проде сделал бы иначе:

- **Нет ограничения частоты входа.** В проде нужен rate-limit по паре «IP + имя» с общим хранилищем, иначе на трёх инстансах лимит утроится.
- **Админом становится первый, кто вошёл как `admin`.** Так разрешает задание. В проде админа лучше создавать при развёртывании, с паролем из переменной окружения.
- **Граница конца раунда.** Засчитывается тап, который дошёл до базы до `end_at`. Если он ждал блокировку строки раунда, запись может завершиться на миллисекунды позже, и итоги, открытые в ту же секунду, могут ещё измениться.
- **Горячая строка счётчика раунда.** Все тапы раунда по очереди обновляют одну строку `rounds`. Для десятков игроков это не заметно. При тысячах игроков в раунде я бы считал итог как сумму очков при завершении или разбил счётчик на несколько строк.
- **`source-map-js` закреплён на 1.2.2** через `overrides`. В 1.2.1 есть уязвимость (GHSA-68fv-2mgg-jv7q), а исправленная версия моложе недельного порога, которым я обычно ограничиваю свежие пакеты. Пакет нужен только инструментам сборки и тестов.

## Что исправлено относительно исходного решения

**Сервер:**

- Тап засчитывался в любое время: проверки, что раунд активен, не было вообще.
- Если игрок не открывал страницу раунда, строки очков не было, и тап падал с ошибкой на `null`.
- Общий счётчик очков раунда не вёлся, хотя этого требует задание.
- Статус раунда записывался как `scheduled` и больше не обновлялся.
- Активность раунда проверялась по часам конкретного Node-процесса. При нескольких инстансах часы могут разойтись.
- Роль admin выдавалась только заранее созданному пользователю, а не по имени. В коде остался тестовый пользователь `roma`.
- JWT подписывался запасным секретом `your-secret-key`, если переменная не задана.
- Несуществующий раунд возвращал 200 с полем `error` вместо 404.
- Таблицы создавались через `sync({ force: true })`, без миграций.

**Клиент:**

- После тапа гусь блокировался на 100 мс, и быстрые тапы терялись.
- `setState` вызывался прямо во время рендера.
- В заголовок раунда попала отладочная строка `к={needReloadOnFinish}`.
- Свои очки не показывались после загрузки страницы, только после первого тапа.
- Обратный отсчёт шёл по часам устройства, а не сервера.
